SIEM Integration via Storage-based Log Forwarding

Integrate IronSKY with your enterprise SIEM for security-incident monitoring and correlation. IronSKY automatically ships security-activity logs to a storage bucket, and the SIEM pulls them periodically.

Method: S3 log forwarding Region: ap-southeast-3 (Jakarta) Latency: next-day (T+1)

Overview

With this method, anomalies and potential threats from the mobile-app side can be monitored centrally in your SIEM dashboard, then analyzed and correlated alongside other enterprise log sources.

It uses a flexible storage-based log-forwarding architecture that is compatible with a wide range of SIEM platforms (Splunk, IBM QRadar, ArcSight, Wazuh, and others). Because delivery is storage-based, there is a next-day (T+1) availability gap: a given day's activity logs become available to pull the following day.

Integration Flow

   Mobile Application + IronSKY SDK
            │  Security Events (real-time)
            ▼
   IronSKY Server / Backend
            │  Periodic log export
            ▼
   S3-compatible Bucket (AWS S3, region ap-southeast-3)
            │  Scheduled pulling / S3 connector
            ▼
   SIEM Platform  (Splunk / IBM QRadar / ArcSight / Wazuh / etc.)

Mobile apps running the IronSKY SDK report events to the IronSKY Server. IronSKY periodically exports logs to the S3 bucket. On your side, the SIEM (or a forwarder host) pulls logs from the bucket and processes them into alerts.

Log Content

Logs contain the security events detected by IronSKY, with the following metadata:

  • Security event type — root/jailbreak detection, high-risk injection, MITM, domain fraud, and others.
  • Device metadata — device UDID, OS version, and device model.
  • Timestamp — the time the event occurred.

Access from SecIron

SecIron provides read-only access credentials to the bucket where your tenant's logs are stored. You receive:

ItemValueDescription
Bucketseciron-<tenant>-eventsS3 container for the logs
Regionap-southeast-3AWS Asia Pacific (Jakarta)
Prefixjson_event/<APP_ID>/Log path for your application
Access Key IDAKIA…Programmatic access identity
Secret Access Key<secret>Secret key; keep it confidential

The Access Key ID and Secret are usually delivered in a single accessKeys.csv file. The granted permissions are limited to s3:ListBucket and s3:GetObject on your prefix — enough to pull logs without being able to modify the bucket.

NoteCredentials are confidential. Store them in a restricted location (e.g. ~/.aws/credentials with permission 600) and never include them in a repository or a publicly accessible document.

Data Format & Structure

Logs are organized by application and date, following this path pattern:

S3 path pattern
s3://<bucket>/json_event/<APP_ID>/<YEAR>/<MONTH>/<DATE>-event.json.gz

example:
s3://seciron-acme-events/json_event/1141/2026/09/2026-09-16-event.json.gz

Each object is one day of logs in NDJSON format (one JSON object per line), gzip-compressed. Example of a single event line:

one event (after decompression)
{
  "udid": "1a2b3c4d-0000-0000-0000-999999999999",
  "app_id": "1141",
  "app_name": "Sample Bank App",
  "Security event": "event_risk_root",
  "Response type": "Pop-up message with close pop-up",
  "Startup time": "2026-09-16 12:51:15.000",
  "os_version": "13",
  "Model name": "Pixel 8a",
  "Region": "Indonesia-Jakarta"
}
FieldDescription
Security eventDetected threat type (e.g. event_risk_root, event_high_risk_MITM_android).
udidUnique device identifier.
Response typeRASP action taken (pop-up, monitoring, etc.).
Startup timeEvent occurrence time on the device.
Model name / os_version / RegionDevice and location context.

1. Prepare Credentials

Store the credentials as an AWS CLI profile named ironsky. Run this on the host that will perform the pulling (the SIEM server or a forwarder host).

~/.aws/credentials
mkdir -p ~/.aws && chmod 700 ~/.aws
cat >> ~/.aws/credentials <<'EOF'
[ironsky]
aws_access_key_id = AKIAxxxxxxxxxxxxxxxx
aws_secret_access_key = <secret>
EOF
chmod 600 ~/.aws/credentials

2. AWS CLI & Access Test

install & set region
sudo apt install -y awscli            # or brew install awscli / yum install awscli
aws configure set region ap-southeast-3 --profile ironsky
verify access
aws sts get-caller-identity --profile ironsky
aws s3 ls s3://<bucket>/json_event/<APP_ID>/ --recursive --profile ironsky | tail

If the file listing appears, access is working. Run this test from the same host that will perform the pulling, so the host's connectivity and network rules are validated too.

3. Pull Logs from the Bucket

aws s3 sync only downloads objects not already present locally, so it is safe to run repeatedly.

sync to a local folder
mkdir -p /opt/ironsky/raw
aws s3 sync s3://<bucket>/json_event/<APP_ID>/ /opt/ironsky/raw/ \
  --profile ironsky --region ap-southeast-3 \
  --exclude "*" --include "*.json.gz" --include "*.tar.gz"

4. Extract & Normalize

Decompress the archives to obtain NDJSON. Recent objects are .json.gz, while historical archives may be .tar.gz — handle both. Because some field names contain spaces (e.g. Security event), normalize them to snake_case so they are easy to write SIEM rules against.

decompress + normalize into events.jsonl
mkdir -p /opt/ironsky/out
# .json.gz  -> NDJSON directly
gunzip -c /opt/ironsky/raw/2026/09/*.json.gz \
  | python3 normalize.py >> /opt/ironsky/out/events.jsonl
# .tar.gz (older archives) -> stream members to stdout
# tar -xzOf /opt/ironsky/raw/2026/01/2026-01-25-event.tar.gz | python3 normalize.py >> /opt/ironsky/out/events.jsonl

Normalization script — save it as /opt/ironsky/normalize.py (also used by pull.sh in step 6):

/opt/ironsky/normalize.py
import sys, json, re
for line in sys.stdin:
    line = line.strip()
    if not line: continue
    try: ev = json.loads(line)
    except json.JSONDecodeError: continue
    norm = {re.sub(r"[^a-z0-9]+","_",k.lower()).strip("_"): v for k, v in ev.items()}
    print(json.dumps({"ironsky": norm}, ensure_ascii=False))

5. Forward to SIEM

Point your SIEM to read events.jsonl as JSON logs. Example for Wazuh:

/var/ossec/etc/ossec.conf
<localfile>
  <log_format>json</log_format>
  <location>/opt/ironsky/out/events.jsonl</location>
</localfile>
SIEMIngest mechanism
Wazuh<localfile> with log_format json
SplunkUniversal Forwarder monitor, or Add-on for AWS (S3 input)
ElasticFilebeat filestream + ndjson parser, or S3 input
IBM QRadar / ArcSightLog source / connector reading the JSON file

Once events are ingested, create rules/correlation in the SIEM to assign a severity per security_event type. Example Wazuh rule:

/var/ossec/etc/rules/ (example)
<group name="ironsky,">
  <rule id="100106" level="12">
    <decoded_as>json</decoded_as>
    <field name="ironsky.security_event">event_risk_root</field>
    <description>IronSKY: rooted device ($(ironsky.udid))</description>
    <group>rooting,</group>
  </rule>
</group>

6. Scheduling

Combine the pull and extract steps into a single idempotent script (one that does not reprocess files already handled), then schedule it. Because data is T+1, a 30-60 minute interval is sufficient.

/opt/ironsky/pull.sh
#!/usr/bin/env bash
set -euo pipefail
BUCKET="<bucket>"; APP="<APP_ID>"; REGION="ap-southeast-3"; PROFILE="ironsky"
RAW=/opt/ironsky/raw; OUT=/opt/ironsky/out/events.jsonl
STATE=/opt/ironsky/processed.list; NORM=/opt/ironsky/normalize.py
export AWS_PAGER=""
mkdir -p "$RAW" "$(dirname "$OUT")"; touch "$STATE" "$OUT"

aws s3 sync "s3://$BUCKET/json_event/$APP/" "$RAW/" \
  --profile "$PROFILE" --region "$REGION" \
  --exclude "*" --include "*.json.gz" --include "*.tar.gz" --only-show-errors

extract(){ case "$1" in *.json.gz) gunzip -c "$1";; *.tar.gz) tar -xzOf "$1";; esac; }

while IFS= read -r -d '' f; do
  key="${f#"$RAW"/}"
  grep -qxF "$key" "$STATE" && continue          # already processed -> skip
  extract "$f" | python3 "$NORM" >> "$OUT"
  echo "$key" >> "$STATE"
done < <(find "$RAW" -type f \( -name '*.json.gz' -o -name '*.tar.gz' \) -print0 | sort -z)
cron
*/30 * * * * /opt/ironsky/pull.sh >> /var/log/ironsky-pull.log 2>&1
NoteThe events.jsonl file grows every day. Apply rotation (e.g. logrotate with copytruncate) so disk usage stays under control and the SIEM's tailing is not interrupted.

Verification

  1. Confirm objects were downloaded: ls -R /opt/ironsky/raw | tail.
  2. Confirm events.jsonl is growing: wc -l /opt/ironsky/out/events.jsonl.
  3. Confirm the SIEM shows events, e.g. on Wazuh check /var/ossec/logs/alerts/alerts.json or the dashboard.

Troubleshooting

SymptomCause & fix
AccessDeniedWrong bucket name or prefix. Make sure it matches your APP_ID.
InvalidAccessKeyId / SignatureDoesNotMatchAccess Key/Secret copied incorrectly. Re-copy from accessKeys.csv.
No file for todayNormal behavior (T+1). Yesterday's logs become available the next day.
Duplicate events in the SIEMThe script is reprocessing old files. Record processed files to stay idempotent.
